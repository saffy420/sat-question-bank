# Practice-test map

Maps every question position in each Bluebook practice test to its question bank ID.
Generated by `build-ptmap.cjs`; do not edit by hand. Outputs hold only IDs, positions and counts.

## Run

```
node tools/ptmap/build-ptmap.cjs
```

Reads `active-ids.json` (repo root), `manual-matches.json` (this folder), every `practice-tests/PT*-questions.json`,
`sources/bluebook-ids.csv` and `sources/bank-check.json`, then rewrites `practice-test-map.json`, `README.md` and
`UNMATCHED.md` in this folder, `public/practice-tests.json` (the app's copy: bank IDs per module in display-number
order, read by the Study Plan's test log) and `public/practice-tests-ext.json` (bank ID -> externalId for every
mapped ID, read only when a student uploads a My Practice export). Output is deterministic; `--out <dir>` writes
everything to one directory instead. The exit code is 1 if any check below fails; the files are still written.

The PDF inputs:

```
node tools/ptmap/extract-pdf.cjs                       # sources/*.pdf -> sources/bluebook-ids.csv (needs pdftotext)
node tools/ptmap/build-ptmap.cjs --bank questions.json # refresh sources/bank-check.json from an /api/questions dump
```

`bank-check.json` holds, for every ID the map or the CSV names, the bank's section, skill, difficulty and answer key
(no question text). It is refreshed only with `--bank`, so a plain run is reproducible from tracked files.

Join: an item's `externalId` is matched exactly against `external_id` in `active-ids.json`, within the
same section. Bluebook's own `questionId` is never used as a join key except as the fallback for exports
with no `externalId` at all (hit rate reported; below 50% the file is unmappable and excluded). Every match is exact or `null`.

`manual-matches.json` holds bank IDs supplied by hand for externalIds that are absent from `active-ids.json`
(14 entries, looked up in the bank). They are used only when the exact match is missing or ambiguous, and only when the section agrees.
`displayNumber` is written as an integer (the exports store it as a string).

## `sequence` layout

| Section | Module 1 | Module 2, block A | Module 2, block B |
|---|---|---|---|
| RW | 0-26 | 27-53 (easy) | 54-80 (hard) |
| Math | 81-102 | 103-124 (easy) | 125-146 (hard) |

Which block is easy or hard is derived from the filename labels across all files (majority vote per label).
Label evidence (files x sections): easy -> block A: 15; hard -> block B: 3.
Every file agrees with its filename in both sections, and every file has exactly one module-2 block per section.
Within each module, `displayNumber` runs 1-27 (RW) or 1-22 (Math) in `sequence` order.

## PDF merge (`sources/bluebook-ids.csv`)

Block 1 = m1, block 2 = easy, block 3 = hard; verified against the exports (PT7 Math hard came from an Mhard
export and equals block 3). The exports win: where they give an ID and the PDF differs, the export ID is kept and
the position is listed as a conflict. A position the exports leave empty is filled from the PDF only when the PDF ID
is in the bank, in the same section, and its printed answer is accepted by the bank's key under `isRight`
(`public/shared/stats.js`); a grid-in answer listing several forms passes when any form is accepted. Skill and
difficulty mismatches only warn (the PDF's names are normalised first, `merge.cjs`). `xyz#####` and
`abcd####` are placeholders and stay `null`. SAT11 rows print no IDs: PT11 comes from the exports, and the PDF's
answers are only a cross-check. The same ID in both easy and hard is legitimate; twice within one module is listed.
